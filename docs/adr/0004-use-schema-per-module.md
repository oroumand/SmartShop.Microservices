# ADR-0004: استفاده از Schema-per-Module

## وضعیت

Accepted

## زمینه

در معماری Modular Monolith، ماژول‌ها در یک process و یک deployment واحد اجرا می‌شوند، اما باید ownership داده‌ها و مرزهای منطقی آن‌ها مشخص باشد.

اگر همه جدول‌ها در یک schema مشترک مثل `dbo` قرار بگیرند، احتمال coupling بین ماژول‌ها زیاد می‌شود. توسعه‌دهنده‌ها ممکن است از یک ماژول مستقیماً به جدول‌های ماژول دیگر دسترسی پیدا کنند یا queryهای cross-module بنویسند.

برای هدف آموزشی کارگاه، لازم است مرز دیتابیس هر ماژول واضح و قابل مشاهده باشد.

## تصمیم

از الگوی Schema-per-Module استفاده می‌کنیم.

همه ماژول‌ها از یک database فیزیکی SQL Server استفاده می‌کنند، اما هر ماژول schema خودش را دارد.

schemaهای اولیه:

- `catalog`
- `ordering`
- `payment`
- `ai`

هر ماژول فقط از طریق DbContext خودش به schema خودش دسترسی دارد.

## پیامدها

### پیامدهای مثبت

- ownership داده‌ها برای هر ماژول واضح می‌شود.
- مرز دیتابیس ماژول‌ها قابل مشاهده است.
- نسبت به database-per-module ساده‌تر است.
- برای کارگاه 4 ساعته عملی‌تر است.
- مسیر مهاجرت آینده به database جدا برای هر microservice قابل توضیح می‌شود.
- از قرار گرفتن همه جدول‌ها در `dbo` جلوگیری می‌کند.

### پیامدهای منفی

- isolation کامل database-per-module را نداریم.
- همچنان امکان فنی query زدن بین schemaها وجود دارد.
- باید از طریق code review، architecture tests و conventionها جلوی نقض مرزها را بگیریم.
- migrationها باید با دقت مدیریت شوند تا هر ماژول فقط schema خودش را تغییر دهد.

## گزینه‌های بررسی‌شده

### همه جدول‌ها در schema مشترک dbo

مزیت‌ها:

- ساده‌ترین حالت
- نیاز به تنظیمات کمتر

دلیل انتخاب نشدن:

- مرز ماژول‌ها را مخفی می‌کند.
- coupling بین ماژول‌ها را افزایش می‌دهد.
- برای آموزش Modular Monolith مناسب نیست.

### Database-per-Module

مزیت‌ها:

- isolation بهتر
- نزدیک‌تر به Microservices
- جلوگیری قوی‌تر از coupling دیتابیسی

دلیل انتخاب نشدن:

- پیچیدگی setup برای کارگاه بیشتر می‌شود.
- مدیریت connection stringها و migrationها پیچیده‌تر می‌شود.
- برای مرحله اول آموزشی بیش از حد سنگین است.

### Schema-per-Module

مزیت‌ها:

- تعادل مناسب بین سادگی و جداسازی
- مناسب برای Modular Monolith
- قابل توضیح و قابل مشاهده برای شرکت‌کننده‌ها

دلیل انتخاب:

- بهترین trade-off برای هدف کارگاه است.
