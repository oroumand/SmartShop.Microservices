# ADR-0006: استفاده از قراردادهای explicit بین ماژول‌ها

## وضعیت

Accepted

## زمینه

SmartShop با معماری Modular Monolith پیاده‌سازی می‌شود. در این سبک، ماژول‌ها در یک اپلیکیشن واحد اجرا می‌شوند، اما باید از نظر منطقی و ساختاری مستقل باقی بمانند.

اگر ماژول‌ها مستقیماً به کلاس‌های داخلی یکدیگر وابسته شوند، مرزهای معماری به مرور از بین می‌روند. برای مثال اگر Ordering مستقیماً به Entity یا DbContext ماژول Catalog وابسته شود، دیگر نمی‌توان Catalog را مستقل تغییر داد یا در آینده آن را به سرویس جداگانه تبدیل کرد.

برای حفظ استقلال ماژول‌ها، باید ارتباط بین آن‌ها از طریق contractهای مشخص، کوچک و کنترل‌شده انجام شود.

## تصمیم

برای ارتباط بین ماژول‌ها از قراردادهای explicit استفاده می‌کنیم.

قراردادهای عمومی و بین‌ماژولی در پروژه زیر قرار می‌گیرند:

```text
src/BuildingBlocks/SmartShop.ModuleContracts
```

این پروژه فقط شامل قراردادهای عمومی خواهد بود، مانند:

- DTOهای بین‌ماژولی
- Integration event contractها
- interfaceهای عمومی مورد نیاز برای ارتباط کنترل‌شده بین ماژول‌ها، فقط در صورت نیاز

ماژول‌ها نباید به مدل‌های داخلی، Entityها، DbContextها یا Infrastructure یکدیگر وابسته شوند.

## پیامدها

### پیامدهای مثبت

- مرز ماژول‌ها واضح‌تر می‌شود.
- coupling بین ماژول‌ها کاهش پیدا می‌کند.
- تغییرات داخلی هر ماژول اثر کمتری روی سایر ماژول‌ها دارد.
- مسیر استخراج یک ماژول به Microservice در آینده ساده‌تر می‌شود.
- تست‌های معماری می‌توانند قوانین وابستگی را بهتر enforce کنند.
- قرارداد ارتباطی بین ماژول‌ها قابل مشاهده و قابل مرور است.

### پیامدهای منفی

- باید در طراحی contractها دقت بیشتری شود.
- ممکن است تعداد DTOها یا event contractها افزایش پیدا کند.
- اگر contractها بیش از حد بزرگ شوند، ModuleContracts می‌تواند به محل نشت مدل‌های داخلی تبدیل شود.
- برای جلوگیری از misuse، نیاز به code review و Architecture Tests داریم.

## گزینه‌های بررسی‌شده

### وابستگی مستقیم ماژول‌ها به یکدیگر

مزیت‌ها:

- ساده و سریع
- نیاز به contract جداگانه ندارد

دلیل انتخاب نشدن:

- coupling شدید ایجاد می‌کند.
- مرز ماژول‌ها را از بین می‌برد.
- تغییرات داخلی یک ماژول می‌تواند ماژول‌های دیگر را بشکند.
- با هدف Modular Monolith سازگار نیست.

### استفاده از SharedKernel برای همه چیز

مزیت‌ها:

- دسترسی آسان برای همه ماژول‌ها
- کاهش duplication ظاهری

دلیل انتخاب نشدن:

- SharedKernel ممکن است به محل دفن business logic تبدیل شود.
- coupling پنهان بین ماژول‌ها ایجاد می‌کند.
- مالکیت مفاهیم دامنه را مبهم می‌کند.

### استفاده از ModuleContracts

مزیت‌ها:

- ارتباط explicit و کنترل‌شده ایجاد می‌کند.
- مدل داخلی ماژول‌ها را مخفی نگه می‌دارد.
- برای آموزش مرزبندی ماژول‌ها مناسب است.

دلیل انتخاب:

- بهترین تعادل بین سادگی، وضوح و کنترل coupling را فراهم می‌کند.
