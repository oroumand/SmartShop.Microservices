# ADR-0014: استفاده از Database-per-Service برای سرویس‌های مستقل

## وضعیت

Accepted

## زمینه

Loyalty و Payments پس از استخراج باید بتوانند مدل داده و Migrationهای خود را بدون وابستگی به Contextهای دیگر مدیریت کنند. استفاده از جدول یا Schema مشترک، استقلال سرویس را از بین می‌برد و امکان دورزدن قراردادهای سرویس را ایجاد می‌کند.

Database-per-Service الزاماً به معنای Database Server یا Cluster فیزیکی جداگانه نیست.

## تصمیم

هر Microservice مالک یک دیتابیس منطقی مستقل، DbContext مستقل، Migration مستقل و Credential مستقل در محیط واقعی خواهد بود.

در محیط کارگاه همه دیتابیس‌ها می‌توانند روی یک SQL Server Container اجرا شوند، اما نام دیتابیس و Connection String آن‌ها جدا است.

هیچ سرویس یا ماژولی اجازه Query یا Join مستقیم روی دیتابیس سرویس دیگر را ندارد.

## پیامدها

### مثبت

- مالکیت داده روشن و enforceپذیر است.
- Migration و استقرار سرویس مستقل می‌شود.
- استخراج یا تغییر فناوری Persistence در آینده ممکن‌تر است.

### منفی

- Join بین‌سرویسی وجود ندارد.
- گزارش‌گیری و ترکیب داده به قرارداد یا مدل Read جدا نیاز دارد.
- تراکنش مشترک میان سرویس‌ها حذف می‌شود.

## گزینه‌های بررسی‌شده

### Shared Database و Shared Schema

رد شد؛ زیرا استقلال داده را از بین می‌برد.

### Shared Database با Schema جدا

برای ماژول‌های داخل Modular Monolith باقی می‌ماند، اما برای Microservice مستقل کافی نیست.
