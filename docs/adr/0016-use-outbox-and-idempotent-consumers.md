# ADR-0016: استفاده از Outbox و مصرف‌کننده Idempotent

## وضعیت

Accepted

## زمینه

ثبت Payment در SQL Server و انتشار پیام در RabbitMQ یک تراکنش اتمیک مشترک ندارند. ذخیره موفق Payment و شکست انتشار پیام باعث می‌شود Ordering و Loyalty از پرداخت باخبر نشوند.

RabbitMQ نیز می‌تواند یک پیام را بیش از یک بار تحویل دهد. اجرای دوباره منطق Loyalty نباید باعث تخصیص دوباره امتیاز شود.

## تصمیم

Payment و Outbox Message در یک تراکنش محلی ذخیره می‌شوند. یک Background Publisher پیام‌های منتشرنشده را به Broker ارسال می‌کند و زمان انتشار را ثبت می‌کند.

مصرف‌کنندگان، شناسه رویداد پردازش‌شده را همراه تغییر Domain در یک تراکنش محلی ذخیره می‌کنند. دریافت دوباره همان شناسه بدون اجرای دوباره اثر کسب‌وکاری Ack می‌شود.

## پیامدها

### مثبت

- فاصله خطرناک میان Commit دیتابیس و Publish مستقیم حذف می‌شود.
- بازپخش پیام امن است.
- تحویل At-least-once به اثر کسب‌وکاری یک‌باره تبدیل می‌شود.

### منفی

- تأخیر کوتاهی میان Commit و Publish ایجاد می‌شود.
- Outbox نیازمند پاک‌سازی و پایش است.
- Idempotency باید برای هر مصرف‌کننده و اثر جانبی طراحی شود.

## گزینه‌های بررسی‌شده

### Publish مستقیم پس از SaveChanges

فقط به‌عنوان Checkpoint آموزشی موقت استفاده می‌شود و طراحی نهایی نیست.

### تراکنش توزیع‌شده

به دلیل پیچیدگی و وابستگی عملیاتی برای این سناریو انتخاب نشد.

### ادعای Exactly-once Delivery

رد شد. هدف، At-least-once Delivery همراه با Idempotent Processing است.
