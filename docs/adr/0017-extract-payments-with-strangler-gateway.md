# ADR-0017: استخراج Payments با Strangler Gateway

## وضعیت

Accepted

## زمینه

پس از اضافه‌شدن Loyalty، لازم است یک ماژول موجود بدون بازنویسی هم‌زمان کل SmartShop به Microservice مهاجرت کند. بازنویسی یک‌باره ریسک و حجم کار نامتناسبی ایجاد می‌کند.

Payments مرز کوچک و قابل فهمی دارد و با رویداد پرداخت موفق به سناریوی Loyalty متصل است؛ بنابراین گزینه مناسبی برای نمایش استخراج مرحله‌ای است.

## تصمیم

Payments با حفظ Core و Adapterهای فعلی در یک Host مستقل اجرا می‌شود و مالک دیتابیس مستقل خود خواهد بود.

یک YARP Gateway ورودی عمومی سیستم می‌شود. ابتدا همه Routeها به SmartShop.Api هدایت می‌شوند و سپس فقط Routeهای Payments و Loyalty به سرویس‌های جدید منتقل می‌شوند.

Payment Service برای دریافت اطلاعات لازم سفارش از یک قرارداد HTTP داخلی و Resilient Client استفاده می‌کند. تغییر وضعیت سفارش از طریق `PaymentSucceededV1` انجام می‌شود.

## پیامدها

### مثبت

- مهاجرت Route به Route و بدون Big-bang Rewrite انجام می‌شود.
- مصرف‌کننده API یک Endpoint عمومی ثابت دارد.
- مرز Module قبلی به نقطه شروع استخراج تبدیل می‌شود.

### منفی

- Gateway یک جزء عملیاتی جدید است.
- تماس هم‌زمان Payments با Ordering به Timeout و Resilience Policy نیاز دارد.
- در دوره مهاجرت باید از Dual Ownership و اجرای هم‌زمان دو مسیر جلوگیری شود.

## گزینه‌های بررسی‌شده

### استخراج هم‌زمان همه ماژول‌ها

رد شد؛ زیرا ریسک، دامنه تغییر و هزینه تست را به‌شدت افزایش می‌دهد.

### تغییر مستقیم Clientها به آدرس سرویس‌های متعدد

رد شد؛ زیرا مهاجرت و توپولوژی داخلی را به مصرف‌کننده‌ها نشت می‌دهد.

### حفظ Payments در Monolith و توضیح نظری مهاجرت

رد شد؛ زیرا بدون اجرای واقعی، ریسک‌های route cutover و data ownership اعتبارسنجی نمی‌شوند.
