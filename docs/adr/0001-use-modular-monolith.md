# ADR-0001: استفاده از معماری Modular Monolith

## وضعیت

Accepted

## زمینه

هدف کارگاه ساخت یک اپلیکیشن آموزشی است که بتواند مفاهیم معماری نرم‌افزار را به شکل عملی نشان دهد.

محصول نمونه، یک مینی فروشگاه اینترنتی به نام SmartShop است که شامل ماژول‌های Catalog، Ordering، Payments و AiSearch می‌شود.

تیم آموزشی می‌خواهد شرکت‌کننده‌ها با مفاهیم زیر به صورت عملی درگیر شوند:

- تشخیص مرز ماژول‌ها
- کاهش coupling بین بخش‌های سیستم
- حفظ استقلال منطق بیزینس از زیرساخت
- ثبت تصمیمات معماری
- نوشتن تست معماری
- بررسی مسیر مهاجرت احتمالی به Microservices

از طرف دیگر، زمان کارگاه 4 ساعت است و نباید پیچیدگی عملیاتی بیش از حد وارد پروژه شود.

Microservices می‌تواند استقلال deploy و scalability بیشتری بدهد، اما برای این کارگاه هزینه‌های زیر را ایجاد می‌کند:

- پیچیدگی شبکه
- distributed tracing
- service discovery
- مدیریت deployment چند سرویس
- پیچیدگی data consistency
- نیاز به messaging یا APIهای بین‌سرویسی
- زمان زیاد برای راه‌اندازی زیرساخت

در نتیجه، برای هدف آموزشی این کارگاه، ورود زودهنگام به Microservices مناسب نیست.

## تصمیم

برای SmartShop از معماری Modular Monolith استفاده می‌کنیم.

سیستم به صورت یک اپلیکیشن واحد اجرا و deploy می‌شود، اما از نظر کد، قراردادها، دیتابیس و قوانین وابستگی، به ماژول‌های مستقل تقسیم می‌شود.

ماژول‌های اصلی عبارت‌اند از:

- Catalog
- Ordering
- Payments
- AiSearch

همچنین دو building block مشترک خواهیم داشت:

- SharedKernel
- ModuleContracts

هر ماژول مالک منطق بیزینس، لایه Application، زیرساخت، persistence و endpoints خودش خواهد بود.

## پیامدها

### پیامدهای مثبت

- پیچیدگی عملیاتی نسبت به Microservices بسیار کمتر می‌شود.
- سیستم برای کارگاه 4 ساعته قابل پیاده‌سازی و توضیح باقی می‌ماند.
- مرز ماژول‌ها همچنان قابل آموزش و enforce کردن است.
- اجرای local ساده‌تر است.
- debugging ساده‌تر است.
- deployment اولیه ساده‌تر است.
- امکان مهاجرت تدریجی برخی ماژول‌ها به Microservices در آینده حفظ می‌شود.

### پیامدهای منفی

- همه ماژول‌ها با هم deploy می‌شوند.
- scaling مستقل هر ماژول در نسخه اولیه وجود ندارد.
- failure isolation در سطح سرویس‌های مستقل نداریم.
- اگر قوانین معماری enforce نشوند، سیستم ممکن است به یک monolith درهم‌تنیده تبدیل شود.
- برای حفظ مرزها باید Architecture Tests و code review جدی گرفته شود.

## گزینه‌های بررسی‌شده

### Microservices

مزیت‌ها:

- deploy مستقل
- scalability مستقل
- ownership مستقل‌تر تیم‌ها
- isolation بهتر در runtime

دلیل انتخاب نشدن:

- پیچیدگی عملیاتی زیاد
- نامناسب بودن برای کارگاه 4 ساعته
- نیاز به زیرساخت بیشتر
- افزایش پیچیدگی consistency و ارتباطات بین سرویس‌ها

### Traditional Layered Monolith

مزیت‌ها:

- ساده و آشنا
- مناسب برای شروع سریع

دلیل انتخاب نشدن:

- مرزهای بیزینسی را به خوبی نشان نمی‌دهد.
- احتمال coupling بین بخش‌های مختلف سیستم زیاد است.
- برای آموزش module boundary و مسیر مهاجرت به Microservices مناسب نیست.

### Modular Monolith

مزیت‌ها:

- تعادل خوب بین سادگی و ماژولار بودن
- مناسب برای آموزش معماری
- قابل توسعه و قابل refactor
- مناسب برای شروع بدون پیچیدگی زودهنگام Microservices

دلیل انتخاب:

- با هدف کارگاه بیشترین هم‌خوانی را دارد.
