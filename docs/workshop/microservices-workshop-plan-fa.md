# طرح کارگاه شش‌ساعته معماری میکروسرویس

## جایگاه کارگاه

این کارگاه ادامه مستقیم کارگاه Modular Monolith است. شرکت‌کنندگان پیش‌تر با تحلیل مسئله، ویژگی‌های معماری، مرزبندی ماژول‌ها، مالکیت داده، قراردادهای صریح، Onion Architecture، ADR، تست معماری و تست کارایی آشنا شده‌اند.

هدف این کارگاه معرفی فهرستی از ابزارهای Microservices نیست. هدف این است که شرکت‌کننده‌ها ببینند یک نیاز کسب‌وکاری چگونه به تصمیم ایجاد یک سرویس مستقل، قراردادهای ارتباطی، مدل سازگاری، کنترل خرابی و در نهایت کد قابل اجرا تبدیل می‌شود.

## نتیجه مورد انتظار

در پایان کارگاه، شرکت‌کننده باید بتواند:

1. تشخیص دهد چه زمانی یک قابلیت کاندید مناسبی برای Microservice است و چه زمانی نیست.
2. مرز سرویس، مالکیت داده و قراردادهای آن را مشخص کند.
3. برای هر تعامل، آگاهانه میان ارتباط هم‌زمان و غیرهم‌زمان انتخاب کند.
4. پیامدهای شبکه، Partial Failure و Eventual Consistency را توضیح دهد.
5. Retry، Timeout و Circuit Breaker را در جای درست به کار ببرد.
6. مسئله Dual Write را تشخیص دهد و نقش Outbox را بفهمد.
7. مصرف‌کننده پیام را در برابر تحویل تکراری Idempotent طراحی کند.
8. مهاجرت مرحله‌ای یک ماژول موجود را با Strangler Fig توضیح دهد.
9. مرز تست‌های Unit، Integration، Contract و End-to-End را تشخیص دهد.
10. هزینه‌های عملیاتی Microservices را در تصمیم معماری وارد کند.

## پیام اصلی

Microservices نقطه شروع طراحی نیست. ابتدا مرز تغییر، مالکیت داده و نیاز عملیاتی را پیدا می‌کنیم؛ سپس فقط در صورتی سرویس مستقل می‌سازیم که ارزش استقلال از هزینه سیستم توزیع‌شده بیشتر باشد.

## الگوی ثابت هر بخش

هر بخش کارگاه با چرخه زیر اجرا می‌شود:

1. ارائه یک مسئله یا خرابی واقعی.
2. تمرین کوتاه فردی یا گروهی.
3. تدریس نظریه موردنیاز برای حل همان مسئله.
4. بازنگری پاسخ توسط شرکت‌کنندگان.
5. نمایش تصمیم مدرس و Trade-offهای آن.
6. ثبت تصمیم مهم در قالب ADR یا Contract.
7. مشاهده تصمیم در کد و اجرای سناریو.

## مسئله آغازین

SmartShop قصد دارد برنامه وفاداری مشتریان را اضافه کند. پس از پرداخت موفق، مشتری امتیاز دریافت می‌کند و می‌تواند موجودی و تاریخچه امتیاز خود را ببیند. قواعد کسب امتیاز ممکن است مستقل از چرخه سفارش تغییر کنند و در آینده کانال‌های دیگری نیز از همین قابلیت استفاده خواهند کرد.

## تمرین اول: نیازمندی و ابهام

هر گروه باید در هفت دقیقه پاسخ دهد:

- رویداد کسب‌وکاری آغازکننده تخصیص امتیاز چیست؟
- شناسه پایدار مشتری چیست؟
- آیا امتیاز بخشی از تراکنش پرداخت است؟
- اگر Loyalty موقتاً در دسترس نباشد، آیا پرداخت باید شکست بخورد؟
- چه داده‌ای باید در Loyalty نگهداری شود؟
- چه چیزی نباید وارد Loyalty شود؟

## نظریه Just-in-time

- Microservice به‌عنوان مالک یک Business Capability، نه یک پروژه کوچک یا جدول مستقل.
- تفاوت استقلال منطقی با استقلال Deploy و استقلال عملیاتی.
- Coupling زمانی، داده‌ای، قراردادی و سازمانی.
- High Cohesion درون سرویس و Low Coupling میان سرویس‌ها.
- Rate of Change و نیاز به استقرار مستقل.
- Fallacies of Distributed Computing.
- هزینه‌های واقعی: شبکه، مشاهده‌پذیری، تست، امنیت، استقرار و On-call.

## تمرین دوم: مرز و مالکیت داده

هر گروه یک Context Canvas کوچک تولید می‌کند:

- مسئولیت Loyalty
- داده‌های تحت مالکیت
- ورودی‌ها و خروجی‌ها
- وابستگی‌های بیرونی
- سیاست سازگاری
- شکست‌های قابل قبول و غیرقابل قبول

## تصمیم پیشنهادی مدرس

- Loyalty یک سرویس مستقل است.
- Loyalty مالک حساب امتیاز، مانده امتیاز و تاریخچه تغییرات است.
- Catalog، Ordering و Payments حق دسترسی مستقیم به دیتابیس Loyalty ندارند.
- تخصیص امتیاز پس از پرداخت موفق انجام می‌شود.
- خرابی Loyalty نباید پرداخت موفق را Rollback کند.
- سازگاری وضعیت پرداخت و امتیاز از نوع Eventual Consistency است.
- شناسه مشتری باید پایدار و مستقل از ایمیل باشد.

## ADRهای جلسه اول

- انتخاب Loyalty به‌عنوان Microservice مستقل.
- انتخاب Database-per-Service.
- ممنوعیت دسترسی مستقیم بین دیتابیس‌ها.
- تعریف نسخه اول قرارداد عمومی Loyalty.

## Checkpoint کد

- ایجاد `SmartShop.Loyalty.Api`.
- ایجاد Core و Infrastructure مستقل Loyalty.
- دیتابیس مستقل Loyalty.
- Endpoint مشاهده مانده و تاریخچه امتیاز.
- Health Check پایه.
- اجرای سرویس در کنار SmartShop فعلی.

## چیزهایی که در جلسه اول نباید گفته شود

- «هر ماژول خوب باید در نهایت Microservice شود.»
- «Database-per-Service یعنی حتماً Database Server جدا.»
- «کوچک‌بودن تعداد خطوط کد معیار Microservice است.»
- «Microservices همیشه مقیاس‌پذیرتر است.»
- «استفاده از Docker یعنی سیستم Microservices شده است.»

## تمرین اول: انتخاب مدل ارتباط

گروه‌ها برای هر گزینه مزیت، هزینه و Failure Mode بنویسند:

1. فراخوانی مستقیم Loyalty هنگام پرداخت.
2. دسترسی Payments به دیتابیس Loyalty.
3. انتشار `PaymentSucceeded` و پردازش غیرهم‌زمان.
4. اجرای منطق Loyalty داخل Payments.

## نظریه Just-in-time

- Request/Response برای پاسخ موردنیاز همین لحظه.
- Event Notification برای اعلام یک واقعیت گذشته.
- Command در برابر Event.
- Temporal Coupling.
- Eventual Consistency و بازه ناسازگاری.
- At-most-once، At-least-once و اثر آن بر طراحی مصرف‌کننده.
- قرارداد Integration Event و تکامل نسخه آن.
- Service Discovery در Docker، Consul و Kubernetes.
- Retry فقط برای خطاهای گذرا و عملیات امن.
- Timeout به‌عنوان بودجه انتظار، نه عدد تصادفی.
- Circuit Breaker برای جلوگیری از شکست آبشاری.

## تصمیم پیشنهادی مدرس

- Payments واقعیت `PaymentSucceededV1` را منتشر می‌کند.
- Loyalty این رویداد را مستقل مصرف و امتیاز را محاسبه می‌کند.
- Ordering نیز برای تغییر وضعیت سفارش همان رویداد را مصرف می‌کند.
- پیام شامل داده لازم برای تصمیم مصرف‌کننده است و مصرف‌کننده برای دریافت داده پایه به دیتابیس تولیدکننده وصل نمی‌شود.
- قرارداد رویداد در پروژه قراردادهای Integration نگهداری می‌شود؛ مدل Domain بین سرویس‌ها Share نمی‌شود.

## آزمایش خرابی

1. RabbitMQ یا Loyalty متوقف می‌شود.
2. پرداخت ثبت می‌شود.
3. امتیاز هنوز تغییر نمی‌کند.
4. سرویس برمی‌گردد.
5. رویداد پردازش و امتیاز اعمال می‌شود.
6. درباره Lost Message و Duplicate Message سؤال ایجاد می‌شود تا جلسه سوم آغاز شود.

## ADRهای جلسه دوم

- استفاده از Integration Event برای واکنش به پرداخت موفق.
- انتخاب RabbitMQ به‌عنوان Message Broker کارگاه.
- پذیرش Eventual Consistency بین Payments، Ordering و Loyalty.
- سیاست نسخه‌بندی Integration Event.
- Service Discovery محلی با Docker DNS و مقایسه با Registry خارجی.

## چیزهایی که در جلسه دوم نباید گفته شود

- «Async همیشه بهتر از Sync است.»
- «Message Broker وابستگی سرویس‌ها را کاملاً حذف می‌کند.»
- «Retry هر خطایی را حل می‌کند.»
- «Eventual Consistency یعنی داده بالاخره حتماً درست می‌شود.»
- «وجود Queue تضمین Exactly-once می‌دهد.»

## نظریه Just-in-time

- مسئله Dual Write میان دیتابیس و Broker.
- Transactional Outbox.
- Inbox یا Processed Message برای Idempotency.
- تفاوت Delivery Guarantee با Processing Guarantee.
- Strangler Fig و مهاجرت Route به Route.
- Branch by Abstraction در مرزهای داخلی.
- مهاجرت مالکیت داده و توقف Dual Ownership.
- Contract Test در برابر Integration و End-to-End Test.
- Health Check سطح سرویس و Dependency.
- Correlation، Trace، Log و Metric.

## تصمیم پیشنهادی مدرس

- Payment و Outbox Message در یک تراکنش محلی ذخیره می‌شوند.
- Publisher پیام‌های منتشرنشده را ارسال و وضعیتشان را ثبت می‌کند.
- Loyalty شناسه رویدادهای پردازش‌شده را با تغییر امتیاز در یک تراکنش محلی ذخیره می‌کند.
- تحویل تکراری مجاز است، اما اثر کسب‌وکاری تکراری نیست.
- Payments با حفظ مدل و قرارداد داخلی خود از SmartShop.Api خارج می‌شود.
- Gateway مسیر Payments را به Host جدید منتقل می‌کند؛ سایر مسیرها همچنان به Monolith می‌روند.
- Payment Service برای دریافت اطلاعات قابل پرداخت سفارش از قرارداد HTTP داخلی Ordering استفاده می‌کند.
- تغییر وضعیت سفارش پس از پرداخت از طریق Integration Event انجام می‌شود.

## ADRهای جلسه سوم

- استفاده از Transactional Outbox.
- الزام Idempotency برای مصرف‌کنندگان Integration Event.
- استفاده از YARP به‌عنوان Gateway و نقطه Strangler.
- استخراج Payments بدون Big-bang Rewrite.
- تعریف حداقل Production Readiness برای سرویس‌ها.

## استراتژی تست

| نوع تست | هدف |
|---|---|
| Unit | قواعد کسب امتیاز و رفتار Aggregate |
| Architecture | جلوگیری از وابستگی Loyalty به پروژه‌های داخلی Monolith |
| Integration | Persistence، Outbox، Inbox و Broker Adapter |
| Contract | سازگاری `PaymentSucceededV1` و قرارداد HTTP داخلی |
| End-to-End | یک Happy Path محدود از پرداخت تا مشاهده امتیاز |

## پایان کارگاه

شرکت‌کننده باید بتواند هزینه‌ای را که در برابر استقلال به سیستم اضافه شد فهرست کند:

- قرارداد شبکه‌ای
- Broker
- سازگاری نهایی
- Outbox و Idempotency
- Gateway
- تست‌های بیشتر
- مشاهده‌پذیری توزیع‌شده
- Pipeline و مالکیت عملیاتی

نتیجه پایانی این نیست که Microservices بد یا خوب است؛ نتیجه این است که استقلال باید هزینه سیستم توزیع‌شده را توجیه کند.
