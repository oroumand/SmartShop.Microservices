# ویژگی‌های معماری SmartShop

## هدف این سند

این سند ویژگی‌های معماری مهم برای پروژه SmartShop را مشخص می‌کند.

در این کارگاه تلاش می‌کنیم تعداد ویژگی‌های معماری را محدود نگه داریم. اگر بخواهیم همه ویژگی‌ها را همزمان بهینه کنیم، سیستم بیش از حد پیچیده می‌شود و برای هدف آموزشی کارگاه مناسب نخواهد بود.

## ویژگی‌های معماری اصلی

### 1. ماژولار بودن

سیستم باید به ماژول‌های مستقل و قابل فهم تقسیم شود.

هر ماژول باید مالک مدل دامنه، منطق کاربردی، زیرساخت، persistence و endpointهای خودش باشد.

نشانه‌های قابل بررسی:

- هر ماژول ساختار پروژه مستقل دارد.
- ماژول‌ها مستقیماً به جزئیات داخلی هم وابسته نمی‌شوند.
- دیتابیس با schemaهای جدا برای هر ماژول تقسیم می‌شود.
- Architecture Tests از نقض مرزها جلوگیری می‌کنند.

### 2. قابلیت نگهداری

کد باید برای شرکت‌کننده‌های کارگاه و توسعه‌دهنده‌های آینده قابل فهم، قابل تغییر و قابل توسعه باشد.

نشانه‌های قابل بررسی:

- هر ماژول از Onion Architecture استفاده می‌کند.
- Core بیزینس از زیرساخت جدا است.
- نام‌گذاری پروژه‌ها، فولدرها و کلاس‌ها شفاف است.
- تصمیمات معماری با ADR مستند می‌شوند.

### 3. تست‌پذیری

مرزهای معماری و رفتارهای مهم سیستم باید قابل تست باشند.

نشانه‌های قابل بررسی:

- Architecture Tests وجود دارند.
- Domain و Application بدون SQL Server، Qdrant و OpenAI قابل تست هستند.
- وابستگی‌های زیرساختی پشت interface قرار می‌گیرند.

### 4. قابلیت تکامل

سیستم باید طوری طراحی شود که در آینده بتوان بعضی ماژول‌ها را در صورت نیاز به Microservice تبدیل کرد.

نشانه‌های قابل بررسی:

- هر ماژول schema دیتابیس خودش را دارد.
- ارتباط بین ماژول‌ها explicit و کنترل‌شده است.
- SharedKernel محدود نگه داشته می‌شود.
- جزئیات Infrastructure یک ماژول به ماژول‌های دیگر نشت نمی‌کند.

## ویژگی‌های معماری فرعی

### 1. کارایی

سیستم باید برای دمو و تست‌های پایه عملکرد قابل قبول داشته باشد.

نشانه‌های قابل بررسی:

- endpoint مشاهده محصولات زیر بار سبک پاسخ قابل قبول دارد.
- endpoint جستجوی هوشمند به صورت جداگانه تست می‌شود.
- اسکریپت‌های k6 برای سناریوهای مهم وجود دارند.

### 2. قابلیت اجرا و استقرار

اجرای سیستم برای شرکت‌کننده‌ها باید ساده باشد.

نشانه‌های قابل بررسی:

- Docker Compose وابستگی‌های اصلی را اجرا می‌کند.
- SQL Server و Qdrant به صورت local اجرا می‌شوند.
- README نحوه اجرای پروژه را توضیح می‌دهد.

### 3. سادگی

سادگی برای این کارگاه یک ویژگی مهم است.

نشانه‌های قابل بررسی:

- Microservices از ابتدا پیاده‌سازی نمی‌شود.
- پیام‌رسانی توزیع‌شده وارد نسخه اول نمی‌شود.
- پرداخت واقعی پیاده‌سازی نمی‌شود.
- احراز هویت در محدوده کارگاه نیست.
- Kubernetes در محدوده کارگاه نیست.

## ویژگی‌هایی که اولویت ندارند

### High Availability

برای نسخه کارگاهی لازم نیست.

### Elasticity

چون سیستم به صورت یک deployable واحد اجرا می‌شود، elastic scaling ماژول‌ها هدف اصلی نیست.

### امنیت پیشرفته

رعایت اصول پایه امنیت مهم است، اما امنیت پیشرفته محرک اصلی معماری این کارگاه نیست.

### Multi-Tenancy

در محدوده کارگاه نیست.

## جمع‌بندی Trade-offها

SmartShop روی ماژولار بودن، قابلیت نگهداری، تست‌پذیری و قابلیت تکامل تمرکز می‌کند.

در مقابل، سیستم از independent deployment، independent scalability و operational isolation صرف‌نظر می‌کند تا پیچیدگی کاهش پیدا کند و پروژه برای کارگاه 4 ساعته قابل اجرا باشد.
